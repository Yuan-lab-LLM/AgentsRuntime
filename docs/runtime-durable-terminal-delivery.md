# Durable Team terminal delivery

OpenClaw, Hermes and the OpenCode Team bridge reserve a private persistent journal slot before handing an inbox message to native execution. The slot records admission, execution start, the immutable terminal event and attempt ID, publication receipt and the final CM acknowledgement. OpenCode consumes the same packaged OpenClaw protocol; its final public answer also enters this journal. Hermes tool subprocesses serialize file changes with `flock`; a single supervised Node gateway owns its private state.

Terminal publication uses the existing exact OpenClaw terminal Lua script. Its dedup key is `claw:team:<team>:completions:delivery-<sha256(eventId)>`; retrying a lost reply does not republish or rerun model/tool work. No additional Lua script is required by the managed Redis bridge. Hermes no longer creates a SET-NX claim before XADD. Redis OOM/disconnection returns a durable pending completion, preserving the completed result and stable attempt. Consumer ACK happens after durable handoff; transport finalization failures are not reported as unexecuted business failures.

Each admitted message physically reserves two 6 MiB banks plus two 128-byte headers. A generation, length and SHA-256 checksum identify the committed bank. Updating a result writes the inactive bank in place, fsyncs its body, then writes and fsyncs its commit header; it needs no replacement allocation. Recovery selects the newest complete valid bank, retaining the previous result after an incomplete write. The 6 MiB payload accommodates the supported 1 MiB tool request, 4 MiB native HTTP response, 64 KiB inbox and metadata together; identical result/resultMarkdown fields are stored once. A response containing JSON escape characters is bounded by its encoded HTTP size.

OpenClaw and Hermes completion schemas and execution entries declare/enforce a maximum 1 MiB encoded JSON proposal. Larger answers must be saved in full as artifacts before submitting references; there is no silent truncation. A violated contract retains the original proposal in the reserved journal/artifact when it fits the supported reservation and keeps execution uncertain, rather than publishing a false failure or rerunning work. Provider/native transcript and CM gateway response/WAL bounds remain part of native execution recovery for output outside this contract. Only pending unmaterialized bodies occupy the banks; delivered bodies use artifact references and small immutable receipt metadata. Existing-result/started identities cannot enter a new serial native execution: they recover delivery or require reconciliation. New native work must pass admission with an empty allocated reservation. This is a bounded per-message contract, not permission for unlimited distinct pending proposals on one identity.

Limits remain 256 unfinished entries per member, 1,024 per Team and 4,096 per journal root. Maximum pending physical reservations are approximately 3 GiB per member, 12 GiB per Team and 48 GiB per root, plus frame headers. Only enabled Team instances allocate slots, on demand; provision the PVC for the intended concurrency and retained artifacts, or admission explicitly refuses work earlier. Admission requires 24 MiB free headroom and fully allocates both banks before external execution. Completed CM-accepted entries atomically become 4 KiB immutable receipts, releasing their actual reserved blocks; separate 64 MiB and 65,536-file ceilings include receipts, scope proofs and compaction headroom. Full outcomes and original envelopes move to existing Team `results` artifacts before compaction; these user-visible retained artifacts consume additional PVC capacity and are not counted as free pending slots. No unfinished or ambiguous record is evicted. The PVC must support in-place writes, file fsync, atomic rename and parent-directory fsync. Device failure/fsync I/O errors are distinct from allocation exhaustion and require reconciliation.

OpenClaw places the journal under its existing persistent runtime state root (`terminal-delivery`). Hermes uses the existing Team shared PVC at `.hermes-redis-team/terminal-delivery`. The global bound is per persistent journal root, not a cross-cluster accounting service; CM Redis admission supplies the global service bound. Preserve these directories and referenced results in native Runtime backup/restore. Do not share one Node gateway state directory between simultaneous gateway processes.

Recovery is bounded to 128 files and a 30-second iteration, with Redis transport deadlines. It runs through existing presence loops and periodic inbox pending probes. OpenCode tool HTTP accepts at most 32 connections and 8 concurrent authorized requests, with request/body/time limits. No unlimited in-memory retry queue is added.

A completed receipt can be deleted only after the read-only CM proof key `claw:team:<team>:__cm_capacity:replay-source-closed` provides schema 1, a committed cursor, verification time, proof SHA-256 and `closed_before_ms` covering the original inbox stream ID. All publications must have durable receipts and the terminal proposal must have a final accepted acknowledgement. Missing or malformed evidence preserves the receipt. An unresolved started execution is never reclaimed. The Runtime must never write this internal proof namespace.

A process death between an external side effect and recording its result is inherently ambiguous. Its durable `started` identity remains pending and requires explicit reconciliation against native execution records; automatic redelivery must not repeat the model/tool action. This change does not claim atomicity across arbitrary external side effects. A correction must use a new inbound identity once the previous completion is immutable. Oversized terminal bodies first persist in the reserved bank before artifact allocation. If disk space is exhausted, recovery retains those complete bytes and retries materialization later. The Redis event carries an explicit full-body link, byte count and digest. Native public answers put that explanation in the existing CM `text` field; the Team UI resolves the canonical `/team/results/...` reference through the authenticated owner-authorized workspace download API, preserving the complete answer without silent truncation.

The active-context watcher uses the same admission, execution and result identity as the serial inbox consumer. A durable submitting marker precedes native injection; known submission survives missing Redis processed markers and auxiliary context files. Unknown submission remains protected rather than automatically steering again. Context generation changes do not remove durable evidence. Hermes flushers re-read records under flock and merge only publication receipts/ACKs after network waits, preserving a concurrently compacted or reclaimed record.

Admission reads do not authorize execution. The serial consumer must win an atomic `admitted` → `started` compare-and-set under the same journal lock used by context submission before invoking any native dispatch. A losing consumer leaves the durable owner and pending inbox record intact; the next recovery pass may finish an accepted owner's transport, while an uncertain owner's pending record stays unresolved. Hermes retains a serial-to-context handoff as accepted queued work, including an explicitly declined steering attempt, so it never reopens serial admission during context retries. Oversized-result uncertainty is a distinct bookkeeping operation and cannot grant an execution claim.

Hermes commits the full context notice and its original active message, assignment, root, revision and generation in the reserved journal before acknowledging the handoff. The 64-entry auxiliary context file is only a mirror. Recovery refreshes up to 64 mirrored identities and scans 128 journal files per pass, with a 30-second bound. It reconstructs queued work after missing files, allocation errors or process death, then checks the original binding and lifecycle before claiming native submission. Queue capacity rejection remains pending. Legacy handoffs lacking that original binding require reconciliation; recovery never binds them to a replacement execution. A committed `submitting` or unconfirmed record cannot be converted to ignored/accepted by a stale observer or transport finalizer. Prepared-request marker evidence can resolve it, otherwise it stays protected without repeated injection. Full handoff contents move to the existing result artifact when an exact accepted completion permits receipt compaction.

## Validation and rollout

All execution and tests run on server54. The focused checks are:

- `node plugins/openclaw-redis-team/scripts/durable-delivery-test.mjs`
- `node plugins/openclaw-redis-team/scripts/durable-delivery-capacity-test.mjs`
- `python3 -m unittest test_durable_delivery` from `plugins/hermes-redis-team`
- `durable-delivery-redis-test.mjs prepare|recover` and `durable_delivery_redis_test.py prepare|recover`, using the explicit isolated marker and `RUNTIME_DURABLE_TEST_STATE`, with a Redis AOF/container restart between phases.
- Existing OpenCode, OpenClaw consumer/contracts and Hermes full suites.
- `durable-enospc-test.mjs` and `durable_enospc_test.py` on a dedicated real 64 MiB tmpfs: actual completion tools, allocation exhaustion, maximum native response, encoded response, process exit before/after frame commit, and later full artifact materialization.
- `durable-context-admission-test.mjs`: actual watcher at 256 pending admissions and restart after native submission with lost processed marker/auxiliary file.
- `durable-claim-race-test.mjs` and `durable_claim_race_test.py`: actual serial consumers with real Redis and durable context claims in both orderings, partial ACK/marker loss and restart; Node also retains an uncertain winning owner without ACK or second execution. Node uses deterministic filesystem scheduling and a negative control restoring the old unconditional consumer transition.
- `test_context_handoff.py` and `context_handoff_process_test.py`: actual Hermes handler with real Redis, queue write/fsync failures, original execution mismatch, capacity rejection, stale observers, concurrent fresh processes, crashes around handoff/native/ACK boundaries and native request proof. Set `RUNTIME_ENOSPC_ROOT` to the disposable tmpfs for real queue allocation exhaustion.
- CM `TestRuntimeLargePublicDeliveryProjectsVisibleAuthenticatedArtifactReference` and `TestRuntimePublicArtifactDownloadUsesTeamOwnerAuthorizationAndFullBytes`, with `RUNTIME_PUBLIC_FIXTURE` generated by `durable-review-regression-test.mjs`.

The OOM fixtures must have their own Redis instance: they change maxmemory to force real noeviction backpressure. They must never target an application Redis. The prepared test fixture uses namespace `cm-database-completion-20261118`, pod `runtime-redis`, default-deny networking and loopback port 33328.

No image or application deployment is part of this source validation. A future immutable Runtime image must be built on `10.130.81.54` and applied using CM's native Runtime upgrade workflow, preferably `ClawManager/deployments/runtime-upgrade/upgrade-runtime.py`. Preserve its preparation, preflight, compatibility, data safety, verification and status recording. An unfinished operation, mismatched hibernation evidence or missing native data-safety support remains a hard stop; do not use direct Deployment image edits or database writes as a substitute.

Multi-turn assignments retain a durable scope proof alongside compact receipts. A later accepted completion may resolve earlier turns only when its CM acknowledgement matches Team, member, root, completion and attempt IDs and the immutable published event matches the exact assignment and revision. New CM assignment/revision fields are checked when present; older CM acknowledgements are bound to the immutable event. Resolved records preserve `resolvedByAcceptedCompletion` and `executionMayHaveOccurred`, including previously ambiguous started turns. Scope proofs and future compaction space count against the receipt budget. Wrong roots, assignments or revisions never free a slot. Unknown or unmatched records still require reconciliation.
